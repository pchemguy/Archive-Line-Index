# GitHub main preparation tracking

Use for `sdd-docs-main` creation/readback, preparation issue lookup/closure, explicit pass-reset reopening and final milestone closure, including direct calls. Load the parent [GitHub backend](github.md) for repository/access, protected authentication and operational-failure rules. The coordinator's [main preparation](../../sdd-manage/references/main-preparation.md) owns readiness, task-only DOCS_TASKS, DOCS_PREPARATION control/decision evidence, Git persistence and the final human checkpoint. This module performs hosted operations only.

## Identity and pre-write projection

Require the actual repository, selected preparation-tracking scope and its request/project-policy source from **sdd-manage**. Before target files or branches are modified, load the running/pinned package's [tracking definitions](../../../assets/DOCS_TRACKING_TEMPLATE.json) and [local task template](../../../assets/DOCS_TASKS_TEMPLATE.md). The JSON supplies the complete standard milestone/issue content and dependencies; the Markdown owns the local preparation tasks. Target PLAN/TASKS and a local DOCS_TASKS are not prerequisites for projection. Use both assets from the same package source.

On resume inspect existing `docs/dev/DOCS_TASKS.md` for task structure/checkoffs and `docs/dev/DOCS_PREPARATION.md` for decisions/control, together with actual Git/provider evidence. Adopt legacy mixed lists through the coordinator; neither target file is a prerequisite for initial projection. Preserve checked progress and valid documents. Check task IDs/names/order and semantic scope against the definitions; disagreement returns to the coordinator rather than regenerating the list, inventing content or overwriting existing objects.

| Object | Identity and content |
| --- | --- |
| Native milestone | Exact title `sdd-docs-main` and plain-text description from the JSON; no description ownership marker or project-specific title generation |
| Nine task issues | Exact ordered DOCS-001–DOCS-009 definitions from JSON, rendered as `[<id>] <name>` and the standard brief fields; issue body markers identify the stable task and preparation scope |

The [input-authoring contract](../scripts/forge-project-input.md#predefined-main-preparation-content) defines the JSON interface and rendering. Use the existing task opening/closing markers from [TASKS projection](github-projection.md), plus `<!-- sdd-forge:docs-scope=main -->` for each issue. These issue markers remain machine metadata; they do not belong in the milestone description. Do not add issue URLs, links to nonexistent target documents, product implementation IDs, phase labels, phase review milestones or another local issue-map file.

With Node/Git available, prefer the [single-call projection utility](../scripts/forge-project.md) in docs-main mode: --remote defaults to origin; optional --tasks defaults to the existing docs/dev/DOCS_TASKS.md, or the bundled task template when that default is absent before initialization. It binds fixed content in memory without a draft file or shell chain. Run --check for outgoing-content review, then --apply --confirm-eligibility only after actual prerequisites hold; use --reconcile-only for readback without creation. An explicit reviewed --request and the [draft helper](../scripts/forge-project-draft.mjs) remain available. Standard preparation needs no agent-authored briefs or dependency inference. Other authenticated clients use the same definitions and renderer contract. Keep drafts/requests outside the target repository before the pre-write gate. The logical request/CLI kind remains `docs-main`. The utility may use only the coordinator-defined [transient projection lock exception](../../sdd-manage/references/main-preparation.md#transient-projection-lock); it grants no other repository writes before complete readback.

1. Enumerate open and closed milestones/issues with complete pagination; exclude PRs. Resolve the milestone by exact title and retained numeric identity, and the issues by stable task/scope markers; validate their content and parentage. Duplicate, contradictory or unmarked same-identity candidates block projection. A same-scope milestone with an unprefixed `docs-main` title or description ownership marker is a conflict, not permission to create another one. Resolve an owned discrepancy through explicit backend reconciliation; the optional utility never renames/overwrites it.
2. Create/reuse the native `sdd-docs-main` milestone and all nine issues from the predefined content. Assign each issue to that milestone, preserving unrelated labels/fields and existing evidence. Reuse completed first-approval issues without reopening them for ordinary later edits; only the explicit reset procedure below reopens a pass.
3. Read back the exact milestone and each issue's marker, identity and association. Return IDs/URLs, created/matched/updated state and unresolved differences. **Only complete verified projection clears the coordinator's pre-write gate.** Partial creation, uncertain writes or inaccessible lookup remain pending; inspect real state before retrying, never create duplicates to evade uncertainty.

GitHub is the projection, not authority for local completion. An existing closed milestone or issue does not prove accepted documents, QC or published integration. Report inconsistent prior closure and resolve its scope/evidence rather than certify readiness from provider state.

### Fixed-content updates on adoption

A newer package may change standard brief text without changing task identities. A saved request using older definitions must be regenerated/reviewed against the selected source. The optional projection utility reports exact-content conflicts; it does not silently migrate them. Before an explicit backend reconciliation, verify the unique marked issue/milestone identities, associations and old standard content. Update only the owned standard brief fields to the selected package definitions through a supported authenticated CLI/API operation, preserving numbers, comments, states, associations and unrelated content; read back exact content. Unknown/custom or ambiguous content returns to the coordinator for resolution, not overwrite or duplicate creation. Reconcile uncertain effects before replay; already matching objects need no write. Retain the adoption basis in DOCS_PREPARATION once repository writes are eligible; before the pre-write gate use only permitted external evidence. This content reconciliation is separate from pass-reset reopening and supplies no missing task acceptance.

## Complete preparation issues

Before closure resolve the unique marked issue, current repository and milestone association. Require the coordinator's actual task completion evidence:

- **DOCS-001:** Original retained/copied outcomes for all four root files, verified preservation/copies, DOCS_TASKS completion, DOCS_PREPARATION initialization evidence and published initialization commit, or verified retained completion. Require completed default provenance setup or an explicit human/project opt-out/deferral in the initialization evidence; an unspecified choice cannot justify omission. No transcript or conversation-URL access is required. A preliminary provenance seed/merge alone cannot close this issue. A mixed-presence continuation pause may remain after initialization is complete.
- **DOCS-002–008:** Approval in the active pass or applicable scoped preapproval, required current-scope QC, and the commit containing the approved document state, DOCS_PREPARATION decision/QC references and corresponding checked DOCS task, pushed with verified containment. After reset, require the completion transition/evidence after that reset, not a previous pass's approval/comment/commit. A prior proposal commit leaves the task/issue incomplete. Resumed recognized approvals retain their actual evidence; do not claim a historical checkbox transition that never occurred.
- **DOCS-009:** Passing whole-package `docs/dev/DOCS-QC-REPORT.md`, DOCS_PREPARATION package evidence, refreshed HANDOFF and checked final DOCS task in one verified published commit; all earlier preparation issue closures verified.

Add a concise evidence comment if absent, close as completed and read back state/reason under the existing issue operational-failure rules. Do not duplicate a matching comment or repeat a verified closure. The coordinator publishes before requesting closure; this backend creates no commits.

Document tasks/issues record development **through first approval in the active pass**. Ordinary later edits leave them complete/closed; current document validity is assessed in the owning workflow/package QC instead. An explicit cursor reset uses the separate reopening procedure below. Implementation task invalidation/reopening semantics do not otherwise apply. A false or unsupported approval claim is a separate evidence defect for the coordinator.

## Reset a document-design pass

Require the coordinator's [recorded reset](../../sdd-manage/references/doc-design-modes.md#reset-the-cursor): actual repository/branch, prior and next pass scope/authority recorded in DOCS_PREPARATION, published reset commit, DOCS-001 retained complete, and DOCS-002–009 locally unchecked. A normal document edit or a request to reconcile projection does not authorize reset. Keep the same milestone and issue identities, titles, briefs, associations and unrelated fields; no per-pass projection or replacement issues are needed.

1. Resolve all eight DOCS-002–009 issues by retained handles and stable main-preparation markers, excluding PRs and validating unique identities and milestone association. Preserve DOCS-001 and its issue. Use complete lookup/readback under the backend failure protocol; ambiguous or unknown identity blocks dependent work.
2. For each issue, add a concise reset-evidence comment with pass/scope and the exact reset commit only if that evidence is absent. Reopen closed issues through the available authenticated GitHub CLI/API issue-state operation, then read back each exact issue as open. Already open issues need identity/evidence verification rather than another state write. Check state before replay after any uncertain response. The optional forge-close/projection utilities do not implement reset reopening; do not invent a CLI flag or treat projection success as reopening evidence.
3. Verify the documentation milestone remains open. Resolve an incorrectly closed retained milestone through supported state reconciliation within the active reset scope; do not replace it or claim prior closed campaign artifacts became editable. Return exact issue/milestone states and remaining effects to the coordinator. Any missing/failed/unknown required reopen blocks resumed document work.

Interrupted recovery reuses the same reset commit and completes only outstanding comments/state changes. A partially reopened set does not allocate another pass. Later issue closure requires the new pass's actual completion evidence. At an autodoc DOCS-008 stop or between autoloop passes, DOCS-009 and the milestone remain open; defer milestone closure until explicitly advanced package QC and verified documentation integration are complete.

## Close the preparation milestone after integration

1. Resolve the unique milestone and all nine issue identities. Read every associated issue, including closed issues, with full pagination; foreign open issues, PRs or ambiguous ownership block closure and must be preserved.
2. Require all nine issues closed from verified completion, passing package QC and evidence of the documentation branch's **explicit two-parent merge into the actual default branch**, merged-state checks, target push and verified remote containment. Closed issues or a pushed documentation branch alone are insufficient.
3. Close the native `sdd-docs-main` milestone and read it back. An already correctly closed milestone needs verification, not another write. Unknown/failed closure stays pending; read actual state before retry. Return the milestone URL/state, completion and merge identities and any unresolved effects to **sdd-manage**.

The coordinator then confirms the final checkpoint before implementation. This preparation operation does not activate implementation objects, select a range or close an implementation phase. Local-only preparation has no hosted writes; it retains the coordinator's applicable local gates.
