# Completion and checkpoints

## Task commit contract

One executable task closes in one task-owned commit. Cumulative multi-task closing commits are forbidden. The closing commit's tree must contain that task's verified result and applicable tests/documentation; its task-owned diff includes the remaining result changes, required current completion evidence or its established link, and the initial unchecked-to-checked transition in owning TASKS or FEATURE-TASKS. The authorized partial-checkpoint condition below governs result portions already committed. Never commit the task result first and defer its completion checkbox to a separate `mark complete` commit. Complete, commit, inspect and publish this boundary before starting another task.

- Use exactly one owning task ID at the beginning of the subject under **sdd-report**'s [task subject rules](../../sdd-report/references/object-drafts.md#task-commit-subjects). A conforming subject cannot make bundled or split closing contents compliant.
- Apply the same contract to code, tests, documentation and explicit milestone/phase review/report tasks. For each milestone's assigned final boundary task (standalone review or final implementation task) and each phase review task, the result includes the [HANDOFF checkpoint update](../../sdd-manage/references/continuity.md#establish-and-refresh) in the same closing commit as the substantive report, acceptance evidence and initial task checkbox. A subject saying “Complete review” without that result does not close it. Do not impose the new handoff format retroactively on pre-adoption historical commits.
- Do not include another executable task's result or initial completion checkbox. Shared files are allowed only when their staged hunks belong to this task or required scoped bootstrap; inspect ownership rather than grouping tasks for convenience. Several verified issue references for one task are not multiple task ownership.
- Eligible milestone/phase parent checkboxes may accompany the final task without counting as extra executable task closure. A justified later parent-only status/evidence follow-up identifies its single owning review/final task and boundary; this exception never permits deferred initial task checkboxes or bundled task results.
- Explicitly authorized partial checkpoints retain the task unchecked and describe incomplete work. Later scoped task-specific repairs retain their actual identity and evidence, without claiming another initial closure. These cases mean one closing commit per task, not exactly one commit ever associated with a task. Non-task campaign, preparation and merge work must not invent task IDs.

When explicitly authorized partial checkpoints already contain some or all production edits for the task result, the closing commit finishes the remaining task-owned work, includes the initial completion checkbox and current evidence, and identifies those checkpoints in that evidence. Inspect the complete resulting task state as well as the closing diff; do not duplicate unchanged code merely to create a production diff. Never relabel an ordinary result-first/checkbox-later violation as an authorized partial checkpoint after the fact.

Before committing, inspect the intended subject and actual staged result, checklist delta and evidence. Identify the one closing task and confirm its exact owning entry and initial completion transition; distinguish parent status from executable task status. Exclude unrelated staged content and another task's hunks while preserving them. If ownership or separation is unsafe, block the commit rather than bundle work. After committing, inspect the actual subject and committed diff against its parent for the same facts, plus remaining staged/unstaged changes, before publishing and advancing. Do not infer compliance from the draft, checkbox, filename or subject alone.

### Task persistence audit and recovery

On continuation, inspect the latest claimed closing boundary and any pending result/status for the selected work. Before integration, audit the task closing commits for the selected completed range through relevant merge parents: each exact owning task ID has its own closing commit establishing the verified complete result, current evidence and initial completion transition together, with referenced authorized partial checkpoints inspected when applicable, without another task's result/closure, and its subject satisfies the task rules. Account separately for authorized partial checkpoints, repairs and parent-only follow-ups. Merge summaries do not substitute for these commits. Keep the audit bounded to the active selected work and established baseline; do not reopen unrelated closed campaigns or require a new registry, hook or journal.

Classify observed problems separately; one task may have more than one:

- **Commit composition:** malformed subjects, bundled task results or split initial result/status. Inspect actual task-owned diffs and parents; current passing tests do not repair that history.
- **Acceptance/evidence:** missing, contradictory, failed or later-invalidated required verification, including premature completion before inspecting a production-test failure. A structurally single-task commit can still make an unsupported completion claim.
- **Ownership/authority:** uncertain task identity, unrelated contents, missing operation scope or a human pause. Preserve work and resolve uncertainty before affected mutation or publication.

Hold affected advancement/integration while the manager resolves these specific gates under the recovery procedure below. Preserve history and valid work: no automatic rebase, reset, force-push, task replay or retrospective issue reconstruction. Never relabel a split closing commit as an authorized partial checkpoint or parent-only follow-up.

### Resolve a task recovery

1. Inspect the task, original closing commit/parents, required acceptance conditions, actual failed or missing evidence, current correction and publication state. Record the separate problem classes and affected task/dependent/parent claims in existing task or campaign evidence. A test count, recovery filename or green command alone does not establish acceptance; identify the corrected condition and exact tested source.
2. Recover the actual implementation grant, selected range/stop, working/target branches, allowed publication/hosted effects and pending human decisions. The manager may resolve an in-scope forward repair under that existing authority, including its verification, task-specific corrective persistence and authorized hosted reconciliation. A repair does not by itself require renewed permission to publish or continue the unchanged range. Ask only for a missing grant, changed scope/contract, human pause resolution or a genuine exception; do not request blanket reapproval of known authority.
3. Route authorized repairs to the active implementation owner. Correct unsupported completion or mark reassessment pending while unresolved; inspect affected dependents and parent exits and coordinate authorized issue/milestone reopening through **sdd-forge**. Preserve original evidence as historical. Reproduce/inspect the relevant failure and verify the corrected condition plus affected regressions against current authoritative acceptance; do not weaken requirements to clear the gate.
4. Inspect the correction's subject and task-owned diff/evidence/status, then commit/push/read back through the established publication procedure. Retain the original task identity and describe a forward correction, not a second initial closure. No mandatory recovery file or new registry is required. A corrected current result does not retroactively validate the earlier completion or make historical composition compliant. If a historical composition violation still blocks integration, an explicit human exception must identify the violated rule and affected boundary; the manager cannot waive it merely because current tests pass.
5. Record which gates are resolved and which remain blocked, current acceptance, correction/publication/hosted state and next eligible work. Continue only inside the retained active range after its applicable gates clear. Stop at its original checkpoint or a genuine unresolved blocker/pause; recovery neither widens the range nor resumes a completed, paused or steering workflow by implication. A previously unsupported verification claim alone needs no historical-composition exception once current acceptance and the other gates are established.

## Complete and commit each task

1. Confirm the intended implementation, relevant tests and documentation, and task-specific verification are complete. Missing or contradictory required evidence blocks completion; a checkbox or green command alone is insufficient.
2. Mark the task complete in its owning TASKS or FEATURE-TASKS. Honor designated project evidence locations; otherwise record concise commands, observed outcomes, condition coverage, relevant state/limitations, and any authorized test-first exception alongside the task or in its existing linked evidence location. Clear its **Completion reassessment pending** note only when current acceptance is established, preserving earlier evidence as historical. Unresolved reassessment retains its note and cannot support a completed claim. Commit identity can be located by the task ID; do not require embedding a commit's own SHA in its content or adding a transaction journal.
3. Resolve hosted issue references through **sdd-forge** when tracking is active. Use **sdd-report** to compose a message with the task ID and verified issue associations, including closing keywords when the commit fully resolves an issue. Never guess an issue number. If hosting is unavailable after the required activation/task projection was verified, retain the verified local result, proceed with its local commit and report unresolved references/closure as pending; preserve confirmed associations. This completion allowance does not authorize task execution across missing initial or added-work projection. For a previously omitted gate, preserve work and use the manager's [omission recovery](../../sdd-manage/references/tracking-decision.md#recover-an-omitted-requested-gate); publish already verified retained commits without replaying implementation.
4. Apply **sdd-manage**'s [repository bootstrap](../../sdd-manage/references/repository-bootstrap.md) before the first SDD commit (after startup pushing); include its owned disclosure, usage notice and README links with the task result. Inspect the final diff and stage only task-owned result, test, documentation, status, and evidence changes. Preserve unrelated staged and unstaged content; do not include it through a blanket staging command. Inspect the staged diff and explicitly exclude unrelated staged content from the commit while preserving its index state. A normal commit includes everything staged, even when only task paths were newly added. Use a path-scoped commit only when the entire selected file content is task-owned, or isolate the selected changes in a temporary index. If task changes cannot be separated safely, report the conflict before committing.
5. Commit exactly this task’s remaining result changes, required current completion evidence and initial completion status together under the [task commit contract](#task-commit-contract). Check the exact leading single-ID subject and resulting committed result/checklist/evidence contents, not just the staged proposal, and inspect remaining staged and unstaged diffs. After a temporary-index commit, ensure the ordinary index does not stage a reversal of the committed owned change; reconcile only its owned entries while preserving unrelated staged content. A checked but uncommitted task is completed pending work, not yet a durable completed task.
6. Confirm retained-commit [publication eligibility](startup-and-continuation.md#push-before-task-work); push the verified task commit and all other eligible outstanding commits on the current branch to the established remote branch as part of the authorized implementation workflow. Required content review ends before the result commit; the host may independently review tool requests crossing its sandbox boundaries. Use the [supervised HTTPS publication entry](../../sdd-manage/references/git-workflows.md#monitor-pending-git-operations) from the initial attempt with deterministic credential selection, diagnosing suspected stalls automatically. Coordinate observed [helper blockage](../../sdd-manage/references/credentials.md#blocked-or-interactive-credential-helper) or credential failure through **sdd-manage**; reconcile pending process/remote effects before recovery retry. Verify remote containment. Complete this push before implementing the next task. If it fails, preserve the commit and report the pending push rather than advancing; use [Git recovery](../../sdd-manage/references/git-workflows.md#platform-authorization-rejection) for a host denial.
7. For active hosted tracking, use **sdd-forge** to close the verified, committed task issue with the task ID, commit, and verification evidence. Reconcile existing closure without duplicate writes. On successful hosted access, also reconcile older pending references and closures for verified completed tasks within the established maintained tracking scope; do not inspect only the latest task. Derive this backlog from owning lists, Git evidence, and hosted state without adding a journal. If hosting is unavailable, retain verified local completion and report closure as pending; never equate hosting failure with implementation failure. Further execution remains subject to verified phase/task projection and dependencies; pending dependent closure or unknown effects cannot authorize review/next-phase progression.

Provide a concise task result through **sdd-report** before advancing within the authorized range. The commit's task ID, checklist, and evidence establish the boundary for startup inspection if execution is interrupted.

## Execute review/report tasks

Apply the [backend object lifecycle](../../sdd-conventions/references/backend-object-lifecycle.md). Execute required standalone milestone/phase review tasks as selected tasks; do not skip or append unselected tasks. Where task generation omitted a standalone milestone review task, perform its assigned whole-milestone review/report obligations within the selected final implementation task, after its implementation is ready and before closing it. This adds no task ID or task count. Use sdd-verify for read-only code review and check evidence, sdd-tdd/sdd-docs for their focused changes, and sdd-report for the committed boundary report. Repair bugs, critical issues and contract violations before review task completion. Include admissible non-critical TODO findings with options/provenance; the final phase review includes the final implementation report when the full list completes. A report draft without completed review/tests is incomplete task work.

Before closing each milestone's assigned final boundary task or the phase review task, automatically refresh `docs/dev/HANDOFF.md` with the verified outcome/evidence, current remaining scope, exact next stop and pending effects requiring confirmation. Phase review also records overall exits and integration readiness. Include HANDOFF with that task's report/result and initial checked status in one commit; one task closing both a review milestone and the phase produces one combined update. Add no handoff task or routine follow-up commit. A failed/blocked review retains actual findings and incomplete status; it cannot produce a successful-completion snapshot. Ordinary intervening task commits require no handoff edit.

After the assigned boundary task's result/report/status is committed, pushed and its issue closed, request sdd-forge milestone closure/readback. A phase review waits for every delivery milestone closure; its final milestone closes after its own review task. Retain pending closures on backend failure; do not infer synchronization from local checkboxes or advance to dependent phase gates. Local-only mode applies the same evidence gates without hosted objects.

## Parent completion and stopping

- Check a milestone only when its constituent tasks, required review/report and applicable PLAN exit conditions are verified; check a phase only when its milestones and phase exit conditions are verified. Empty or blocked groups are not complete by default.
- Reassess flagged parent claims against their current exit conditions; correct unsupported checked status and retain the pending note until those conditions are established. A resolved task reassessment alone does not clear its parent's note.
- In FEATURE-TASKS, a parent checkbox covers only that list's scoped work and relevant FEATURE-PLAN exits. It does not check the corresponding whole-project milestone or phase in TASKS.
- Commit and push parent status and any additional boundary evidence with the final task when available, or in a focused parent-only follow-up commit with the leading single owning task ID and relevant parent boundary. This does not permit separating the task’s initial completion checkbox from its result. Do not invent a new task solely to record parent status; boundary evidence already belongs to its assigned task under accepted PLAN/TASKS. Hosted closure remains a separately observed state, not authority for local acceptance.
- Do not start tasks beyond the requested task count, milestone, phase, or named checkpoint, even if further tasks are ready. Integrate only when the workflow gate is met; a completed main task subset in an incomplete phase pushes and pauses without a merge. Also stop for an unresolved implementation or push blocker or the user's pause instruction.
- Report implemented capabilities, completed IDs, acceptance and exit-condition evidence, unresolved failures or limitations, commit and push state, pending issue reconciliation, and remaining tasks. Distinguish task/working-branch completion from integration into the established target and its remote publication.

After the requested stopping boundary, the human decides whether to resume the main task list or command **sdd-steer** for a focused amendment. Do not start either automatically after the selected checkpoint.

## Integrate the completed boundary

Use **sdd-manage**'s **Git workflows** reference after the selected tasks and applicable exits are verified, committed, and pushed. Task persistence remains per task. For main development, merge once for a complete verified phase; a smaller requested range pushes and pauses on its phase branch. For feature work, use [phase/campaign delivery](../../sdd-manage/references/feature-delivery.md): default integration requires a completed phase, phase-matched incorporation and retention of future sources; a narrow incomplete phase pushes/pauses. Revision work integrates only its coherent authorized boundary. Verify the entire prospective branch difference before integrating: an existing branch containing unrelated or unfinished work is a scope conflict. A pause or blocker returns branch state without a partial merge.

For a complete feature implementation request, coordinate incorporation of the accepted feature documents and task ownership required for its final main-document consistency through **sdd-integrate-feature**, on the working branch before final verification. An explicit selected document set governs incorporation. A narrow task/range request does not authorize incorporation of all feature documents or integration of unfinished work: merge only when the selected branch difference and documents are coherent within that scope; otherwise report the unmet prerequisite. Retain active sources and pending reassessment until their established requirements are satisfied.

When the applicable integration gate is met, verify working-branch acceptance, then merge with an explicit two-parent commit, verify the merged state, and push the target. **sdd-manage** coordinates this Git integration; a direct invocation follows the same protocol. Report task completion separately from branch acceptance, target integration, and published merge status. A merge failure does not erase previously verified task commits; it blocks the workflow's integrated completion. Stop after this boundary without selecting additional tasks or steering.

## Affected orientation checkpoint

Apply the manager's [agent orientation](../../sdd-manage/references/agent-orientation.md) when material source/layout/check commands, governing links or active task/feature ownership changes within this workflow. Preserve controlling manual instructions and update affected root AGENTS.md with the verified owned checkpoint. Feature archive/transfer keeps current canonical owner links accurate; historical checklists are not duplicated as executable owners. Explicit path limits or real policy conflicts return to the manager. An unchanged startup requires no rewrite.
