# Git branch management

Use this coordinator procedure for mutating branch setup, reuse, continuation, and authorized phase transitions. Apply **sdd-conventions**' **Workflow identity** rules; use [Git workflows](git-workflows.md) for explicit integration/publication. Local Git operations require no hosting backend. Execution/steering owners retain their commits and pushes; sdd-orient observes state without branch mutations.

## Establish context and identity

1. Use current orientation to identify eligible worktree, actual branch/HEAD, applicable instructions, pending-change ownership, authorized workflow/range, and accepted sources. Read-only review or selection creates no branch. Implementation applies its [publication preflight](../../sdd-implement/references/startup-and-continuation.md#push-before-task-work) and pushes eligible outstanding commits on the current established branch before task work or new branch setup; never create a branch to evade a push blocker.
2. Establish working branch, target, starting checkpoint, relevant HEADs and remote destinations. Project preparation resolves the actual repository default branch from remote/project evidence; do not guess `main` or `master`. Its target is that default branch. Main implementation identifies its actual main integration branch explicitly; revision/feature implementation targets may be that branch or the active phase. Steering targets the paused implementation branch. For a revision nested within another active campaign, apply [revision modes](revision-modes.md#nested-revision-campaign): default source and return target are the actual parent campaign branch, with parent execution suspended. A prefix proves neither target nor ownership.
3. Allocate or recover the convention's campaign identity for revision/steering/feature, or the owning PLAN/TASKS phase number for main implementation. Inspect reviews, features, phase-nested revisions and relevant remote state for allocation/collisions. Record the full baseline, creation parent branch and branch-off commit, actual working/target identities, scope, and active source links in existing campaign/task/change evidence and the entry HANDOFF before dependent work. New workflow branches start from and integrate into that same parent; history corroborates but cannot always identify an original branch name. Preserve explicit overrides and established legacy associations; resolve consequential ambiguity rather than retargeting or rewriting them. Preparation-only can reserve identity without authorizing implementation.
4. For revision/steering, ensure the workflow-specific revision directory/record matches the branch identity; steering uses the owning phase report directory's revisions prefix; a steering report can begin with objective/context and gain verification results later. For feature preparation, record campaign identity, full baseline, branch/target, scope and active sources in FEATURE_PREPARATION under the [feature preparation contract](feature-preparation.md); reserve the associated features-directory identity for later evidence/archive without creating another preparatory navigation artifact. Main documents remain in docs/dev. Do not fabricate optional review stages or a second registry.

## Create or reuse

- For a closed revision amendment, establish [reopened campaign eligibility](revision-modes.md#eligibility-and-authority) before reuse; retain its original identity and record the new source/target checkpoint. An active blocked workflow resumes rather than reopening.
- Reuse only when context, history, target and pending work fit the same scope. Preserve suitable legacy/in-flight names or explicit project/user overrides and their recorded association; no automatic migration.
- For new work, choose the workflow convention's branch name and validate it with `git check-ref-format --branch`. Inspect local/remote name collisions and worktree occupancy. An unrelated occupied name needs a distinct slug suffix without changing campaign identity; remote uncertainty is not proof the name is free.
- Create project preparation branches from the refreshed default parent. After the gate below, create implementation branches from their recorded integration parent containing the verified/published preparation baseline; other scoped branches also start from their established parent checkpoint. Use a separate worktree where unrelated dirty work or target availability requires it; preserve original staging/work and never implicitly stash/reset/clean. Do not check out one branch in two worktrees.
- An unborn/detached/conflicted state, missing usable checkpoint/target/remote, unresolved ownership or inability to establish identity blocks setup. Report the concrete decision/facility rather than guessing a different destination.
- Publish branch checkpoints through the active owner's ordinary Git push and verify remote containment; do not create the same remote ref through a duplicate API operation. This manager needs no sdd-forge branch capability or PR workflow.

## Main phase lifecycle

Release placement is separate from implementation/campaign integration: follow the [release commit/tag boundary](git-workflows.md#release-commit-and-tag) to create the release commit on the actual default branch, directly or as the merge from the designated primary development branch. Completing a phase or revision on another branch does not make its tip a release source.

Before the first implementation branch, complete the preparation integration gate below. Later phase branches still require the preceding phase's verified integration/publication. A new accepted preparation delta must pass the same gate before a new dependent implementation branch.

Apply [phase activation](phase-activation.md) before the phase's first task and every authorized next-phase transition. Hosting reads the complete plan but projects only the eligible phase. Require explicit review units and confirmed phase objects when tracking is active.

Select main-project work on the owning `phase/<number>-<slug>` branch. A bounded task or milestone request within an incomplete phase ends with verified commits/pushes and a paused phase branch, not a merge into main. Record completed range, remaining phase work, applicable evidence and current target context.

When all phase work, delivery and phase reviews/reports, applicable hosted milestone closures and exit evidence are complete, use the Git protocol for one explicit merge into the established main integration branch, verify the merged state, publish, and confirm containment. A checkbox or completed subset is insufficient. Failed exits or publication retain branch/merge state; do not create the next phase.

Only when the request authorizes further work, create the next phase branch from the updated verified/published main checkpoint and re-establish its scope. Split an authorized cross-phase range into sequential phase segments; each phase must meet its exit before the next branch starts. Do not execute extra tasks or perform an unrequested continuation to fill a phase. An explicit instruction to integrate a partial phase is a recorded override with its scope/evidence consequences, not the default.

For feature-owned multi-phase delivery, use [feature phase delivery](feature-delivery.md) for its persistent campaign branch, per-phase incorporation/integration and next-phase synchronization. Main phase branch rules above do not rename feature branches or imply early feature archive.

Feature/revision integration into a phase updates that phase's accepted inputs and evidence; it does not complete the phase. Steering returns control after its amendment merge. Standalone revision/feature boundaries retain their own accepted scope and integration gates.

## Continuation

Use [continuity](continuity.md#select-the-continuation-branch) for startup branch discovery/selection and recovery since HANDOFF. Compare each candidate with its recorded parent and remote publication; a child integrated into its unfinished parent is not independently pending because main lacks it.

Recover identities and actual file paths from retained records and Git; names alone do not prove state. Distinguish incomplete phase work, pending archive/reconciliation, uncommitted merge, completed merge awaiting push, and an already integrated campaign. Resume the same authorized operation rather than allocate another identity or repeat an existing merge. Report ambiguous ownership/target and preserve valid work. Retain branches unless deletion is explicitly requested or covered by project policy.

## Preparation integration gate

Before initial design-docs/main setup, main initialization performs the [default provenance scaffold](ai-logs.md#fresh-main-setup) on reserved `design-docs/ai-logs` unless an explicit human/project override disables or defers it. That narrowly scoped seed/merge is preliminary DOCS-001 work, not project-document preparation or completion. Unspecified choice does not skip setup. Apply the procedure below to normal preparation; provenance setup waives no pre-write, publication or ownership gate.

The default branch is the repository's actual configured default, commonly `main` or `master`, but any valid name is supported. Discover it from remote/project evidence and carry that exact branch and remote destination through merge, push and implementation handoff. The conventional preparation name `design-docs/main` denotes initial project preparation; its suffix does not select the default target.

Apply this gate to initial project preparation, feature preparation, and accepted project-document preparation needed by a revision, including direct calls to document owners. Preimplementation project documents include PROJECT, ARCHITECTURE/DECOMPOSITION and children, SPEC, PLAN/layout, TASKS and feature counterparts, their required adjacent QC reports, main DOCS_TASKS, DOCS_PREPARATION and DOCS-QC-REPORT, feature FEATURE_DOCS_TASKS, FEATURE_PREPARATION and FEATURE-QC-REPORT, and applicable root orientation/disclosure/discovery records. Commit these owned artifacts on a dedicated design-docs branch before implementation. Campaign review/revision plans and reports remain on the campaign revision branch; they are outside this gate. Document amendments and task/status evidence produced during already active implementation or checkpoint steering remain with that scoped working branch; do not relocate ongoing execution or historical records.

1. **Prepare separately.** For fresh/resumed main or feature preparation, establish its enabled hosted pre-write gate under [main](main-preparation.md#establish-preparation-before-repository-writes) or [feature preparation](feature-preparation.md#establish-preparation-before-writes) before creating/reusing a branch through any mutating operation. Before authoring project preparation documents, establish `design-docs/main` for initial preparation or `design-docs/<campaign>-<slug>` for scoped preparation. Create it from the refreshed default checkpoint; validate names, collisions and worktree ownership. Preserve the campaign suffix where applicable. Keep implementation and campaign review/revision artifacts off this branch. Commit and push coherent project-document/QC checkpoints there through coordination persistence.
2. **Honor the boundary.** Completed main preparation, including preparation-only, follows [main preparation](main-preparation.md): DOCS-009 package QC, issue closure, explicit documentation merge/verification/publication, then `sdd-docs-main` milestone closure and the final human checkpoint before implementation. Apply the [doc-design mode boundary](doc-design-modes.md#complete-a-pass) first: autodoc stops/resets at DOCS-008 before package QC or integration. Earlier requested document stops remain stops. Feature preparation follows [its corresponding FDOCS-009/QC, published integration and milestone sequence](feature-preparation.md#final-package-qc-integration-and-checkpoint); feature autodoc first stops at FDOCS-008 before package QC/integration. Other preparation-only paths finish with committed/pushed documents on design-docs and stop. A request that authorizes implementation also authorizes the prerequisite preparation merge and publication; do not request the same authority again. An explicit unmerged/local-only boundary is honored and blocks dependent implementation when the required published baseline cannot be established.
3. **Establish readiness.** Identify the exact accepted preparation tip, its owned paths, current document QC evidence, and actual default target. Inspect the full branch difference, including older commits. Unaccepted decisions, unresolved required reviews, unrelated changes or implementation mixed into the preparation difference block integration; preserve work and resolve ownership rather than merging it by implication.
4. **Integrate preparation first.** Use [Git workflows](git-workflows.md#merge-verify-and-publish) for a two-parent explicit merge into the refreshed default branch, merged-state verification, target commit and publication. This preparation boundary is eligible independently of implementation phase completion. Record preparation tip, target parent, merge commit and publication in existing navigation or handoff evidence; revision campaign evidence remains on its revision branch. A failed merge, check or push stops the transition before a new dependent implementation branch is created.
5. **Verify containment and branch afterward.** Confirm `git merge-base --is-ancestor <preparation-tip> <default-tip>` succeeds and the established remote contains the verified default merge. After publication succeeds, verify that the intended implementation parent contains that accepted baseline. If the parent is an active phase rather than default, first propagate the verified preparation through an authorized scoped [incoming synchronization](git-workflows.md#merge-purpose), verify and publish that parent, inspecting the full incoming difference. Preserve the receiving phase's identity, HANDOFF and unfinished boundary. Do not merge unfinished phase work into default or change targets to evade this prerequisite. Then create the execution branch from that refreshed parent and record its branch-off commit; its final integration returns to that same parent. Missing authority, unrelated incoming changes or incompatible histories block affected setup.
6. **Resume from evidence.** A previously integrated preparation tip needs containment/publication verification, not another merge. Campaign-only review/revision work can create its revision branch and persist campaign records without a design-docs stage. If that revision also needs new project preparation, preserve its campaign branch, complete the project-document gate separately, and incorporate the published default checkpoint into the existing revision branch through [incoming synchronization](git-workflows.md#merge-purpose) before source implementation; retain that revision's identity, parent and unfinished boundary. For an already created but unused implementation branch, check baseline containment before use. Preserve branches with existing implementation and report a missing baseline as a prerequisite conflict; do not reset, replay tasks or silently merge unfinished implementation into default.

Ready QC reports and a pushed design-docs branch do not establish the default-branch baseline. Preparation integration does not complete any task, phase, feature incorporation, hosted projection or product acceptance. Record these states separately and retain design-docs branches unless deletion is authorized.

**The default-branch push is mandatory after the preparation merge.** Push the verified merge commit to the actual default branch and verify remote containment before creating a dependent implementation branch. Carry the existing request, repository/ref, merge SHA, document scope and checks through coordination. A failed push retains the merge and blocks implementation; use [Git recovery](git-workflows.md#platform-authorization-rejection) for a host denial.

## Descriptive directory association

For new revision, feature and phase-nested steering packages, reserve `<campaign>-<slug>` with the matching complete branch suffix. Discover both suffixed and established unsuffixed directories by their stable sequence/baseline prefix; different slugs do not permit duplicate sequence reservations. Record collision suffixes and actual paths in existing context. Continuation uses that association; never migrate retained directories from the default alone.
