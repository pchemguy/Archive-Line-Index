# Feature phase delivery and campaign completion

Load for feature implementation selection, phase transitions, incremental incorporation/release or final campaign integration. **sdd-implement** owns task/range execution, **sdd-integrate-feature** owns scoped main-document incorporation, **sdd-manage** owns eligible Git transitions and **sdd-forge** owns selected hosted/release effects. This mapping reuses the shared execution/review discipline; it creates no second task list or implementation progress ledger.

## Establish the phase and branch mapping

After [feature preparation](feature-preparation.md#final-package-qc-integration-and-checkpoint) has passed its published integration gate, create the recorded `feature/<campaign>-<slug>` implementation branch from its verified creation parent. Record the exact parent/baseline and authoritative FEATURE-TASKS/FEATURE-PLAN or incorporated owning lists. The preparation default merge and a feature's final creation-parent target can differ; verify propagation when the implementation parent is an active phase. Do not merge an unfinished parent phase into default.

Keep this campaign branch across its delivery phases. A feature can contain one or several bounded phases; one feature does not imply one phase. Phases use project-wide accepted identity/dependencies, shared milestone/phase review and selected tracking. A feature does not allocate a main `phase/*` branch merely because its owning list contains phase headings. Reports retain the campaign feature prefix; FDOCS preparation objects and product T-task objects remain separate.

## Execute and integrate a completed phase

1. Select the exact authorized task/milestone/phase segment and stop from the current owning list, preserving external main-task dependencies. Apply [phase activation](phase-activation.md), document readiness and projection/readback. For a later feature phase, require its predecessor's completed exits, review/report, selected hosted closures and verified target integration/publication. A range crossing phases executes sequentially; an incomplete phase pushes and pauses without integration, unless the human explicitly directs a scoped partial integration with its consequences recorded. Do not append unselected tasks to manufacture a phase exit.
2. Execute shared single-task persistence, verification and milestone/phase review/report gates. Before the closing phase review checkpoint, coordinate the [phase-matched accepted incorporation](../../sdd-integrate-feature/references/feature-incorporation.md#incremental-phase-incorporation) needed for coherent delivered behavior/main documents. Retain exact accepted source clauses, completed phase scope and future feature boundaries in existing phase/task evidence. Required report/HANDOFF, incorporation/rechecks and initial phase-review checkbox close coherently under the task contract; no new administrative review task is invented.
3. Check the full prospective campaign-branch delta against the recorded receiving target. It may contain the previously published complete feature preparation and genuinely future active deltas; it must not contain unverified future implementation, another campaign's work or unsupported claims of completion. Retain future work as intended scope in its active sources; do not present it as delivered or widen completed-phase exits. Resolve ownership/conflicts rather than guessing a cherry-picked subset.
4. Explicitly merge the exact verified campaign tip into the recorded receiving target with two parents, verify the merged result and regressions, publish/read back and confirm containment. The merge summary identifies campaign/phase, original opening/baseline, actual scope, both parents, relevant review/verification and remaining feature work. A phase merge completes only that phase; it does not close the entire feature campaign or archive sources still needed by later phases. Retain task/issue/milestone scope so a feature parent never closes a larger main-project parent.
5. If a release is authorized for this phase, run its existing default-branch release protocol only after the relevant integrated source is verified there. A merge into an active phase alone is not eligible release placement; missing accepted default integration/authority is a specific unresolved boundary, not permission to merge an unfinished parent. Distinguish requested artifact delivery, unavailable native verification and actual release publication. A phase merge by itself selects no release.
6. Before the next authorized phase, reconcile release/target changes and any pending issue/milestone/merge/push effects. Bring the published receiving baseline into the retained campaign branch through verified [incoming synchronization](git-workflows.md#merge-purpose) when needed; preserve campaign identity, creation parent and remaining scope. If the target equals an already contained campaign tip, verify that state rather than create an empty merge. Then activate only the next eligible phase and proceed within the retained range. A requested pause or exhausted range returns control instead of auto-continuing.

## Final feature boundary and recovery

Only after all requested feature phases/work, selected reviews/closures and required main-document/task consistency are complete does the final phase/campaign boundary qualify for final incorporation/archive. Coordinate the remaining accepted delta and unique task ownership, then archive only sources whose active dependents and evidence disposition permit it, under the [incorporation procedure](../../sdd-integrate-feature/references/feature-incorporation.md). Preparation checklists/records/reports are archived as historical evidence, not main product requirements. Retain future or externally owned work explicitly when a narrower authorized campaign boundary is selected; never claim the complete feature from a partial range.

Complete final source/report/HANDOFF and task persistence audits before its eligible merge; verify/publish the recorded target and return under continuity. A final merge already represented by a verified published phase integration is inspected/reused; do not fabricate another merge merely for a closure label. Final archive/source disposition not yet integrated needs its own coherent verified/published boundary. Closure requires actual effects and clean return, not the merge-message title alone.

After interruption, recover the campaign branch/parent, current phase/range, accepted incorporation scope, active/archived source state, owning task evidence and actual remote/hosted effects. Finish a retained incorporation, merge, push or release through its owner; do not replay tasks, allocate a new campaign or duplicate completed merges. Failed feasibility checks and required unknown operations retain their gates, while unavailable native/full-browser checks follow the project's existing scoped policies.
