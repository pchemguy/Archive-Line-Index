# Comprehensive prerelease review

Use when the human explicitly selects comprehensive review of a release candidate. This provider-independent profile supplies scope and criteria to [review and revision](review-and-revision.md); use its campaign lifecycle and sdd-report's [campaign artifacts](../../sdd-report/references/campaign-artifacts.md) rather than a separate framework. Release callers load only the [advisory reminder](#advisory-release-reminder) unless review is selected.

## Advisory release reminder

At entry to a requested release creation/completion or a workflow run that will publish a product release, briefly recommend this review and explain that it can be selected explicitly. Apply this to coordinated and direct release calls, including publication triggered by a tag push. For example: “A comprehensive prerelease review is recommended for this candidate and can be requested separately; it is optional, and I will proceed with the authorized release checks.”

Emit the reminder once for the selected release operation; pass its disposition through the normal handoff to prevent duplicate reminders by the coordinator and publisher. Reuse a known human decision or an applicable candidate-specific review, acknowledging its actual coverage when useful. Do not fabricate a decline, waiver or review selection from silence. If the candidate changes, identify any resulting evidence limit without automatically starting review or requiring it to proceed.

The reminder is advisory: do not ask for confirmation, pause or delay an authorized release, activate review, require a waiver, or add a mandatory gate. If the human explicitly selects review before publication, honor that requested sequence and its report boundary. Highlights-only work, package assessment and build-only/workflow preparation do not themselves trigger this publication reminder or authorize release publication.

Ordinary required source, package, workflow and publication checks still apply under the accepted project contract and [release checks](../../sdd-verify/references/release-checks.md). Optional review does not replace them, clear a known required-check failure, or grant publication authority. A review's readiness assessment is evidence for the human, not an additional universal release gate.

## Establish candidate and plan

1. Establish the selected project, governing instructions, supported product scope, release intent, exact candidate source SHA and relevant version/package identities. Pin supplied package hashes and provenance; distinguish source-only review from assessment of actual built bytes. Record pending changes, the inspected/tested states and authorized checks/effects. A moving branch name alone is not the candidate identity.
2. Inventory the complete CURRENT supported product: governing contracts/design, implementation, tests, workflows, public documentation, entry points and distribution assets. Use the release diff and risk to prioritize depth, not limit coverage to changed files. Account for generated/third-party material and exclusions with reasons. Apply the [closed-record boundary](../../sdd-conventions/references/review-campaigns.md#closed-campaign-records): exclude closed campaigns and historical feature/steering snapshots from routine loading and current-validity checks. Selected historical consultation answers only a specific evidence question and creates no compatibility repair duty.
3. Create the campaign review plan with bounded units, owner routing, dependency order, criteria and representative success/failure/boundary/recovery scenarios. Identify tools, permitted local/external checks, unavailable facilities and exclusions. Adapt criteria to the actual project; record not-applicable concerns with reasons rather than inventing product requirements or mandatory artifacts.
4. Assess each unit using the selected focused owners below. Review consequential handoffs on both sides. Record no-finding coverage, blocked/deferred units and evidence classes: source inspection, consumer assessment, actual execution or authorized external verification. An example inspected is not an example executed; structural support tests are not live agent/client acceptance.

## Findings, readiness and rechecks

Use stable finding IDs and the existing report format. Each canonical finding records baseline location/evidence, observation and consequence, type (defect, evidence gap or improvement recommendation), priority, confidence, bounded proposed correction, dependencies/needed decisions and objective recheck. Do not confuse a recommendation with an accepted requirement; retain actual acceptance, rejection and deferral separately from observed evidence.

After each planned unit, update and commit the review report; the coordinating workflow pushes and verifies remote containment before any next unit or additional work under [per-commit publication](git-workflows.md#publish-each-commit). Consolidate coverage, findings/counts, dependencies, unavailable checks and readiness against the pinned candidate and existing required release criteria. Separate evidenced blockers, accepted deferrals, optional improvements and unknowns. Record actual human decisions; do not invent risk acceptance or infer global readiness from passing structural tests.

When the source, contract or package changes, identify affected units, handoffs and dependent regressions and reassess them against the new exact candidate. A previous report remains evidence for its own source, not automatic readiness for the new candidate. Reuse unaffected evidence only with its provenance and justified applicability. Accepted repairs use the existing revision procedure and owner workflows; recheck their objective criteria before marking findings Verified.

## Complete and stop

Return the published report, assessed source/package, coverage/readiness, canonical proposed revision queue and concrete evidence limits. Review assessment ends at its report commit; coordination completes its authorized publication. Stop before source repairs, revision execution, release/tag creation or publishing workflow dispatch unless those effects are independently authorized. Selecting this profile does not select hosted tracking or authorize external checks with write effects.
