# Activate an eligible phase

For FEATURE-TASKS execution, use the [feature phase/campaign mapping](feature-delivery.md): retain its campaign feature branch, verify predecessor phase integration/publication and do not create a main phase branch or close the entire feature merely from a phase exit.

Use the [backend object lifecycle](../../sdd-conventions/references/backend-object-lifecycle.md), current orientation and accepted PLAN/TASKS. Preparation can describe all phases locally; it does not create all hosted objects or authorize execution.

1. Resolve the owning phase, selected range, prerequisite evidence, actual integration target and established tracking mode. For the first phase, no predecessor is required. For later phases, require completed predecessor delivery/phase reviews and reports, applicable local exits, all hosted milestones closed when tracking is active, and required verified target integration/publication. A phase label is historical association, not a completion state.
2. Confirm explicit review tasks and final single-task phase review milestone already exist in accepted planning. Missing hierarchy/exits require their owning amendment before execution; do not fabricate them during startup.
3. Before creating the first or a newly dependent phase branch, confirm [preparation integration](branch-management.md#preparation-integration-gate): accepted project documents and QC reports are merged, verified and published on the actual default branch. Establish/reuse the eligible phase branch under branch management, preserving later phases' predecessor integration gate. When tracking is selected by request or applicable project policy for this repository/scope, request sdd-forge projection for this phase only, reading full owning lists for identity/dependencies. Require readback of its label, every milestone including review milestones, and every task issue including review tasks with initial associations before task implementation edits or task test execution. No objects yet is pending projection, not a local-only decision. Missing, partial, unavailable or unknown projection blocks affected execution; local-only continuation across this gate requires an actual explicit human override with recorded scope.
4. Hand off eligible tasks, exact phase identity, report prefix, applicable exits, actual tracking decision/source and verified object identities/associations or a concrete projection blocker to sdd-implement. A local TASKS checklist, phase branch or inactive note cannot substitute for required hosted readiness. Reuse still-applicable verified evidence; recheck affected state after material changes or uncertain effects, not merely for ceremony. Respect count/boundary selection. Never create later-phase objects or run later tasks solely because the full backlog is available.

On continuation, recover the same phase identity and confirmed objects rather than allocating another phase. Finish missing creation/associations with readback and preserve unrelated objects. Before next-phase activation, reconcile pending task/milestone closures and existing merge/publication; unknown effects block that transition. Independent further task execution is limited to an already verified activated phase and tasks with satisfied projection/dependencies. Added or materially changed task associations require affected projection/readback before execution; an outage does not waive this prerequisite.

When forge selects its optional [local projection mechanism](../../sdd-forge/scripts/forge-project.md), pass the actual confirmed scope/readiness and source identities under its [input contract](../../sdd-forge/scripts/forge-project-input.md). The agent enriches dependency/brief semantics and reviews the outgoing payload; a local extractor or positive JSON flags do not establish these gates. Consume projection_verified with current associations or retain the concrete pending/conflict/unknown blocker. The coordinator still decides activation eligibility and execution handoff.

## Preparation readiness before projection

Before creating the eligible phase's hosted objects or starting its first task, establish current owning TASKS/PLAN/SPEC readiness under [document QC gates](document-qc-gates.md). This adds no administrative task or phase and does not activate future phases. Resolve focused missing assessment within scope; stale or confirmed blocked inputs stop dependent projection/execution. Existing issue/milestone closure still follows verified implementation lifecycle evidence, not a document Ready label.

## Optional tracking decision at handoff

Use **sdd-manage**'s [tracking decision](tracking-decision.md) before dependent phase activation. Carry the recommendation, actual confirmation/decline, repository/scope and observed hosted state separately. A supplied GitHub token recommends enabled tracking but does not activate it; unresolved activation choices return to the manager. Reuse confirmed scope without repeated approval. Late confirmation reconciles retained evidence instead of replaying product tasks.
