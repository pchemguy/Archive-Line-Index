# Hosting credentials and shell recovery

**sdd-manage** owns accepting, discovering, saving, and supplying tokens and recovering shell authentication. Apply **sdd-conventions**' **Hosting tokens** rules. **sdd-forge** and its active backend own provider-specific access requirements; implementation/steering and coordinated persistence retain their Git push ownership. Ordinary local work requires no hosting token.

## Deterministic Git publication

Use the [supervised publication entry](../scripts/git-auth-recover.md) from the first authorized HTTPS push/readback. Auto mode uses an already supplied eligible conventional repository token immediately, bypassing inherited selectors with command-local configuration. If the token is absent, existing noninteractive authentication receives one supervised attempt. A present invalid/ineligible token is a local input failure; do not silently switch accounts or request a replacement merely because a helper hung. Explicit existing mode preserves a selected suitable existing mechanism. No credential store/configuration changes or authentication probes are a prerequisite.

The utility owns the finite process lifecycle; the active publication owner still supplies the established destination/ref/expected object and applies [Git workflow outcomes](git-workflows.md#monitor-pending-git-operations). Missing runtimes/ownership facilities are concrete blockers, not permission to launch an unbounded raw push. Other operations/transports require their own supported bounded facility. API operations may use their available authenticated client; Git success does not establish API access.

On an explicit credential/provider failure retain sanitized repository, destination/endpoint, attempted operation, client/transport and cause. Classify rate limits, policy and transport failures before choosing a remedy. Preserve implementation's outstanding-push prerequisite and established destination.

## Blocked or interactive credential helper

On supported evidence that the pending operation is waiting on a helper or unavailable interaction, investigate automatically under the existing operation grant; do not wait for a completed 403 or ask the user to initiate diagnostics. Follow the Git lifecycle for bounded observation, owned-process disposition and uncertain remote effects. A timeout alone is not evidence that the token is invalid. GIT_TERMINAL_PROMPT controls Git's terminal prompting, and helper-specific interaction flags apply only where supported; neither is a general deadline or a guarantee that arbitrary helper UI is disabled.

For an earlier independently launched blocked helper, settle that owned attempt before using the supervised entry for readback/recovery. Reuse a suitable protected token under its runtime/input prerequisites rather than alter persistent configuration merely to unstick the call. Apply the [preparation write gate](#authentication-before-main-preparation-writes) and token eligibility rules before supply. If the original push outcome is uncertain, select readback first and settle the owned pending attempt before another push. Missing facilities require a concrete retained blocker or another supported protected mechanism; they do not authorize early storage or automatic software installation.

Persistent helper/store setup remains an intentional alternative when justified within the actual recovery scope. Establish the reason, affected account/repository context and existing state before changing it; preserve prior helper multivalues and unrelated credentials. A local helper assignment does not itself clear inherited helpers: inspect the effective chain and use an appropriate empty reset when replacing it. Local Git configuration and vault entry scope are separate; use consistent path/context handling when repository isolation is intended. Do not erase or restore other credentials blindly, or request renewed permission for work already authorized. Retain sanitized diagnostic basis, selected mechanism/effects and actual publication outcome in existing evidence; distinguish reported assumptions from observed facts.

## Authentication before main preparation writes

While enabled preparation projection under [main](main-preparation.md#establish-preparation-before-repository-writes) or [feature](feature-preparation.md#establish-preparation-before-writes) remains unverified, defer the storage procedure below. Use available authenticated API access; HTTPS Git follows the supervised selection above. Reuse a repository token only if read-only checks already establish its required exclusion, untracked status and readability; do not modify ignore rules to make it reusable before projection.

For an actual authentication failure or an observed blocked helper eligible for transient recovery, use a suitable supplied token or request one with the active backend's permission profile. Consume it through a supported protected transient client channel, with any helper outside the target repository. Keep values out of helper source, arguments, URLs, logs and evidence. Do not write a token, ignore rule or repository authentication configuration before the projection gate clears. An unavailable protected transfer mechanism is a concrete blocker, not permission to write early or claim access.

After complete docs projection/readback and documentation branch setup, resume **Find, request, and save** using the accepted credential without requesting it again. Complete required exclusion/storage and persist owned ignore changes through ordinary scoped Git publication before dependent preparation continues. A temporary authenticated session does not establish durable storage. After interruption, reconcile actual projection and pending storage before replay; preserve the token convention and report unavailable continuity accurately.

## Find, request, and save

1. Resolve the eligible repository root and active backend. Prefer its conventional file beside the root `.gitignore`: `gh.tkn` for GitHub. Check other suitable `*.tkn` candidates only within this repository, excluding nested Git worktrees and unrelated repositories. Resolve ambiguous suitability rather than guessing; file presence does not prove identity or access.
2. Ensure `*.tkn` is in the root `.gitignore`, preserving existing rules. Create it if missing. Check effective exclusion and untracked status for the selected path before reading for reuse or saving. Correct a conflicting ignore rule within the authorized credential scope; already tracked credentials require explicit remediation. Preserve unrelated staging and work; persist only owned ignore-rule changes through the ordinary scoped commit/push workflow.
3. If a suitable token exists, use it for the affected client's authentication. If none exists or the selected token is unsuitable, ask the user for a suitable replacement, identifying the target repository, operation, and backend-required permission profile. Prefer fine-grained repository-scoped tokens when available; the GitHub profile is defined by its backend.
4. Save the accepted credential in the selected conventional file beside `.gitignore`, after the exclusion checks. Replace only the selected credential when the provided token is intended as its replacement; preserve unrelated files. Do not record its value in ordinary project files, handoffs, evidence, diagnostics, history, arguments, or URLs.

If storage, effective Git exclusion, or supported protected credential transfer is unavailable, report the concrete blocker and retained operation state. Do not claim persistence/authentication happened or silently select another repository. The ignored token file is durable credential input; an external helper may hold a session copy but is not the required source of continuity.

## Authenticate and resume

- **Git shell:** Select a suitable existing helper, the eligible bundled transient utility, or another supported protected facility under the recovery conditions above. For HTTPS Git, feed credentials through protected process input; never embed the token in arguments or remote URLs. A successful store acknowledgement is not authentication/publication evidence. Scope the mechanism for the repository and actual configuration. HTTPS tokens do not authenticate SSH; preserve the established transport/destination and report a required transport decision rather than rewriting it implicitly.
- **Bundled publication utility:** Use [git-publish.mjs](../scripts/git-publish.mjs) with Node.js 22+, Python 3.11+ and required Git/OS ownership facilities under its [CLI guide](../scripts/git-auth-recover.md). Carry the established repository, remote, effective push URL, full ref and expected object. For linked worktrees, an explicit credential-source worktree must share the verified Git common directory; no token copy is needed. The script selects the eligible token/existing route before transport, supervises it, confirms cleanup, and performs exact readback within one deadline. Unknown/different state needs reconciliation; cleanup uncertainty blocks another attempt. Matching does not prove API access, release-source peeling or which attempt wrote the ref. The main-preparation storage/write gate remains controlling. No automatic software installation or unbounded fallback.
- **API client:** Use suitable existing authentication or supply a token to the selected backend through its supported protected mechanism, separately from normal handoff text. For an available gh, follow the [GitHub CLI procedure](../../sdd-forge/references/github.md#github-cli) for existing authentication or protected provided/saved-token supply. Do not assume a connector supports token replacement or that Git authentication updates it; report an unsupported client mechanism precisely.
- **Diagnosis:** For bundled recovery, inspect push_result/readback_result separately from the remote observation. An absent ref does not explain why a push failed. An allowlisted helper_error is an advisory local diagnostic, not authenticated provider denial or permission evidence; see the CLI guide for its exact contract. Reproduce a deterministic helper/context failure locally before another evidence-based push retry, keeping credential protocol stdout protected. Do not replace credentials merely because Git could not obtain them from a helper.
- **Retry:** Retry the affected authorized operation after recovery and confirm its actual result. Use the project's bound or at most three recovery retries; stop on repeated unchanged denial or a restriction requiring a different remedy. A replacement token proves no permission until the operation succeeds.
- **Publication:** The push owner verifies remote containment before further dependent work. Preserve local commits and report pending publication if recovery fails. Authentication does not authorize new operations, another destination, force-pushing, or repository-policy bypass.

A direct **sdd-forge** caller may supply a token without a manager handoff. Follow the same convention when persistence is requested; otherwise consume it transiently through the protected client mechanism. Coordinate durable storage with sdd-manage rather than implying a directly supplied token was saved.

## Non-credential failures

Do not request replacement credentials for rate limits, outages, invalid input, or policy restrictions a token cannot remedy. Use provider timing and bounded retry guidance, preserving successful independent results and pending/unknown effects. After an uncertain hosted write, the backend re-reads affected identities/state before replay; after an uncertain push, inspect the established remote before declaring publication or retrying. Report sanitized causes and limits without exposing credentials.

## Scope through recovery

Keep the existing request scope, destination and payload through credential recovery; recovering authentication does not require a new publication grant. Use the scripted first-attempt path above; changes to credentials or persistent mechanisms require the actual recovery conditions and scope. Preserve/report a host denial through [Git recovery](git-workflows.md#platform-authorization-rejection); replacing credentials cannot resolve a policy restriction.
