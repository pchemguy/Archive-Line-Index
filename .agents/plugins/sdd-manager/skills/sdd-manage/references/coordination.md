# Coordination protocol

## Establish scope and prerequisites

- **Request:** Capture the objective, inspection or mutation mode, target paths or documents, owning task list, selected boundary and allowed external effects. Carry the selected core workflow/variant or standalone operation, decision basis and continuation/stage-change/switch disposition under [workflow selection and continuity](workflows.md#workflow-selection-and-continuity). Reuse session authorization and decisions.
- **Orientation:** Reuse a sufficient current **sdd-orient** handoff; obtain scoped observations where relevant evidence is missing or stale. Establish the repository, applicable instructions, baseline, pending changes, tooling and task evidence before selecting/reporting the path. Do not mistake an unchecked task or latest maintenance commit for a proven execution boundary.
- **Git:** Require an eligible worktree for repository mutations. Outside Git, continue discussion or inspection and report the mutation blocker; do not initialize a repository implicitly.
- **Pending work:** Establish ownership of dirty paths. Preserve unrelated staged and unstaged changes. Do not reset because the tree is dirty. Pass interrupted task implementation to **sdd-implement**, document incorporation to **sdd-integrate-feature**, and commanded amendment continuation to **sdd-steer**; if it lies outside the requested new scope, resolve that conflict before overlapping mutations.
- **Inputs:** Confirm the authoritative requirements, design, strategy, and layout needed by the selected stage. File presence alone does not establish acceptance or consistency.
- **Document readiness:** Use [document QC gates](document-qc-gates.md) before dependent PLAN/TASKS generation, implementation or hosted projection. Compare actual reviewed/governing state and coverage; route missing focused review within scope instead of trusting file presence or a Ready label.
- **Preparation baseline:** Project preparation documents and their QC reports are committed/pushed on design-docs. Complete [preparation integration](branch-management.md#preparation-integration-gate) into the actual default branch before creating a dependent implementation branch. Campaign plans/reports remain on the campaign revision branch. Carry actual preparation tip, default merge/publication and implementation starting checkpoint through the handoff.
- **Tracking execution gate:** Before dispatching phase task execution, load [tracking decision](tracking-decision.md) and [phase activation](phase-activation.md). Carry explicit requested/confirmed scope separately from observed projection. Required objects/associations must be verified before task edits/tests; otherwise hand off a blocker, not executable readiness. Preserve local preparation/human acceptance boundaries and use existing handoff evidence, not a new registry.
- **Proactive handoff:** At entry, preparation handoff, phase activation and completion, identify relevant capabilities, prerequisites, unresolved user choices and coordination gaps. Record the concrete next owner/action, workflow decision and basis, observed state, pending human checkpoint and stopping boundary in the existing handoff. Give the canonical selection brief in user-visible chat; an internal handoff alone does not satisfy it. Use [tracking decision](tracking-decision.md) for optional hosting; ask only when the missing decision affects the next dependent work. Do not create an unrelated administrative task chain.
- **Facilities:** Check availability of the selected skills and necessary tools on the actual execution host under applicable user/repository instructions; reuse current unchanged host/tool evidence. Report concrete missing capabilities. Use ordinary filesystem, Git, and available provider tools; require no particular client, hidden hooks, or implicit installation mechanism.
- **Historical scope:** Use current authorities and the active campaign. Discover prior identities/paths without loading old contents; consult selected history only for a specific current question. Keep [closed records](../../sdd-conventions/references/review-campaigns.md#closed-campaign-records) unchanged and outside current compatibility checks. Inspect proposed paths before staging/integration for incidental edits to closed packages.

For branch workflows, use [branch management](branch-management.md) for setup and [Git workflows](git-workflows.md) for final integration. Preserve implementation's push-first prerequisite; a direct focused invocation uses the same protocol.

## Scope checks and reporting detail

Before each coherent work unit, check the active objective, authorized outputs/effects, applicable instructions and pending human decisions against current evidence. Reuse sufficient context; refresh missing or materially changed evidence rather than repeating orientation for every command. Before creating or editing any user file, verify both the target path and the proposed change belong to the authorized scope. Withhold out-of-scope changes and report a consequential conflict; an allowed path does not authorize unrelated changes within it. These checks require neither narrated reasoning nor new permission for routine authorized work.

At workflow entry, uncertain-context recovery or a material operation/stage/scope change, give a concise chat brief identifying the workflow or operation, current stage/owner, authorized work/outputs and next human checkpoint or stop. Explain consequential selection with its request/project evidence under [workflow selection](workflows.md#workflow-selection-and-continuity). During unchanged work, report new results, decisions or blockers; repeat only scope information needed to understand a change. Routine questions can receive direct answers.

Honor the human's requested reporting detail, including later adjustments. Reduced detail may compress briefs and omit unchanged context, routine explanations and unrequested exhaustive source inventories. Continue to report consequential decisions, scope changes, blockers, verification results and required human checkpoints; fulfill explicit requests for sources or explanation. Reporting detail changes neither authorization nor approval, verification, publication, tracking or stopping requirements. Do not choose detail from presumed model strength or create a separate verbosity-state artifact.

At a human checkpoint, present substantive review results, the dependent work held and what acceptance would clear, following [human document review](human-document-review.md). During clarification, restate the pending boundary when omitting it could imply acceptance or advancement; do not repeat an unchanged full brief on every response.

### Reporting profiles

Use **Standard** for established work unless the human selects another profile or gives a more specific reporting preference. Composite-workflow bootstrap uses the temporary Explicit reporting below. Profiles control presentation; all retain the scope checks, reporting triggers, consequential information and workflow obligations above.

| Profile | Reporting detail |
| --- | --- |
| **Minimal** | Compress entry/scope-change briefs, results, blockers and required human decisions. Omit routine narration, unchanged context and unrequested explanations. |
| **Standard** | Give concise briefs at entry/material changes, useful progress updates and rationale for consequential decisions. |
| **Explicit** | Clearly identify workflow/operation, stage/owner, authorized outputs and next checkpoint at entry/material changes. Give fuller consequential decision rationale, relevant sources and verification evidence without repeating unchanged information on every response. |

Accept ordinary requests such as “Use SDD Manager with minimal reporting,” “Switch to explicit reporting” and “Return to standard reporting.” Retain the selected profile in available conversation/workflow context until changed and carry it through existing handoffs. Do not create a settings file or infer a profile from model strength. If no preference is recoverable, use Standard; do not pretend a lost selection was restored.

A specific request controls its affected output: “Explain this decision fully, then resume minimal reporting” supplies a one-response override and returns to Minimal afterward. A request for an explanation or sources alone does not switch the ongoing profile. Required human checkpoints remain substantive under Minimal; Explicit adds detail rather than approval gates or repeated preambles.

### Composite-workflow bootstrap reporting

Use **Explicit** reporting while establishing a composite workflow at initial entry, a material workflow switch, or recovery that must reconstruct its context. This is workflow-context bootstrap, distinct from repository disclosure/file setup. Routine continuation, task handoffs and minor evidence refresh do not restart it. Honor more specific human limits on bootstrap reporting within their stated scope.

1. Proactively announce the active bootstrap level and briefly explain the choices: **Minimal** reports essentials; **Standard** adds useful progress and consequential rationale; **Explicit** adds fuller scope, sources and evidence. Mention that “Switch to minimal/standard/explicit reporting” changes subsequent detail. Give this explanation once during each applicable bootstrap, not on every response.
2. Establish and report the workflow, stage/owner, authorized work, next checkpoint and consequential evidence or uncertainty under the selection/scope protocols. Explicit reporting is not exposed reasoning or permission to guess missing approvals, task ranges or project readiness. Blocked recovery reports its known state and missing decision without beginning dependent work.
3. Before the dependent handoff/work, announce the subsequent level: **Standard** by default, or the human's established selected profile. The temporary bootstrap level does not replace that selection. If a preference was lost and cannot be recovered, identify the Standard fallback rather than claim restoration. Carry the subsequent level through existing handoffs; no new confirmation or reporting-state file is required.

## Coordinate execution

1. Give each responsible skill the objective, scope, authoritative inputs, decisions, relevant task IDs, branch/HEAD, dirty-path ownership, permitted effects, required evidence, stopping point and selected reporting profile or more specific preference. Carry the actual human grant, destination/ref, payload scope and explicit limits through handoffs; do not ask each worker to obtain the same approval again. Keep credentials out of ordinary handoff text.
2. Let the skill perform its owned procedure. Collect its changed paths, observed evidence, findings, and remaining differences before the next dependent stage.
3. Refresh the material baseline when HEAD, instructions, project, target scope, or relevant pending changes change. Do not repeatedly run orientation or checks when the current evidence remains applicable.
4. Resolve missing human decisions and out-of-scope requirements without guessing or silently expanding work. Continue independent authorized work where possible. Once a commit awaits publication, the per-commit rule takes precedence: finish its inspection/publication/recovery without advancing independent work or making another commit. State the blocked operation and decision needed.
5. Return verification failures to the active workflow's coordinator or authorized artifact owner for repair and recheck. Preparation corrections follow [document QC gates](document-qc-gates.md); implementation repairs remain with **sdd-implement** or **sdd-steer**.
    - **Invalid implementation completion:** apply [task recovery](../../sdd-implement/references/completion-and-checkpoints.md#resolve-a-task-recovery) using existing authority. Distinguish acceptance repair from historical composition exceptions; retain the authorized range and publication scope.
    - **Standalone verification:** return findings without starting repair.
    - **sdd-docs governing amendment:** follow its [referral to the user](../../sdd-docs/references/review-and-findings.md#governing-document-amendments). Preparation correction authority does not bypass that decision.
6. Stop at the requested boundary. A checkpoint is not permission to select another milestone, start steering, incorporate unselected feature documents, or create hosted objects. Complete explicit integration/publication when its workflow gate is met; incomplete main phases push and pause even when the requested task subset is complete. A human-commanded steering amendment always returns control without resuming implementation.

## Persist repository changes

Use this procedure for document preparation, accepted integration, and standalone maintenance. Do not duplicate the commit workflows owned by **sdd-implement** or **sdd-steer**.

- **Policy:** Honor the user's commit and push instructions and repository policy, including standing session instructions. Apply [per-commit publication](git-workflows.md#publish-each-commit): push and verify each workflow-owned commit before advancing work or making another commit. Only an explicit user-directed local-only/deferred-publication instruction changes this cadence within its scope. Do not invent a remote branch or force-push.
- **Verification:** Inspect the actual diff and run checks appropriate to its effects: document consistency and links for authoring, relevant tests for test changes, or **sdd-verify** for acceptance campaigns. Verify heading spacing and project conventions. Do not manufacture task completion for document-only work.
- **Bootstrap:** Fresh/resumed main preparation first follows [main preparation](main-preparation.md): enabled hosted projection before writes, separate DOCS-001 four-file initialization, and README links at PROJECT. For other adoption, before the first SDD commit, apply [repository bootstrap](repository-bootstrap.md): package-derived root disclosure and usage notice plus README links travel with the first owned result. Reuse existing valid records; respect explicit path limits.
- **Staging:** Stage only owned changes; inspect the staged diff and exclude unrelated pre-existing staged paths from the commit. Preserve their index state. A normal commit includes all staged content; use a path-scoped commit only for wholly owned file contents, or isolate selected changes in a temporary index. Stop if ownership cannot be separated safely. Avoid broad staging or destructive cleanup.
- **Commit:** Use **sdd-report** to compose an evidence-backed message. Include stable task IDs and verified issue references when the change belongs to those tasks; main preparation uses its predefined DOCS IDs and atomic first-approval completion; other preparation without assigned tasks does not invent IDs. Inspect commit contents and remaining staged and unstaged diffs; after a temporary-index commit, reconcile stale committed owned index entries while preserving unrelated staged content.
- **Push:** Use the canonical supervised HTTPS publication entry from the first attempt under the [bounded Git-operation lifecycle](git-workflows.md#monitor-pending-git-operations) from the initial attempt through verified remote readback. Diagnose a suspected stall automatically; an observed blocked helper can enter [shell recovery](credentials.md#blocked-or-interactive-credential-helper) without a completed credential error. Reconcile the pending attempt/effects before retrying the same authorized push. Report a committed-but-unpushed result if access, destination, divergence or unresolved process/remote state blocks persistence; retain local work and pause advancement/further commits. Resolve divergence without discarding changes or force-pushing.
- **State:** Distinguish committed, pushed, and hosted status. A successful local commit does not establish remote persistence or issue closure.

## Return results

Use **sdd-report** for the result format. Include the fulfilled objective and affected artifacts or task IDs, observed verification and gaps, commits and push status when applicable, hosted changes or pending reconciliation, unresolved decisions, and the boundary reached. Keep planned work distinct from implemented functionality. Follow [continuity](continuity.md) for the durable HANDOFF checkpoint and reconstruction from subsequent documents, decisions and Git. Conversation-only decisions cannot supply cross-agent recovery. Require no additional transaction journal, recovery directory, issue map or new skill.

## Diagnostic and findings handoff

Return instruction source, actual user choice/grant, observed state and evidence limits separately when explaining omissions. Persist explicit amendment notes under the authorized [review/revision findings procedure](review-and-revision.md#retain-requested-amendment-findings), reporting conversation-only, written, committed, pushed and implemented states truthfully.

## Coordinate environment recovery

On a relevant environment/tooling blocker, coordinate investigation of reasonable supported alternatives within authorized scope before declaring the work blocked. Route technical investigation to the affected execution workflow; implementation uses [environment recovery](../../sdd-implement/references/environment-recovery.md). Preserve partial work, require actual attempt/capability evidence, disclose material substitutions and resolve consequential scope/requirement decisions. Bound investigation by real constraints rather than an arbitrary retry quota. For a host denial, retain the pending operation and report the observed reason; do not reframe it as a tooling failure or switch tools to evade it.

## Human document handoffs

Apply [human document review](human-document-review.md) at entry and each newly created root/proposal. Pass actual presented scope/state, human decision or pending review, technical readiness and authorized next action separately. A multi-stage request still pauses after each necessary new document unless explicitly covered by applicable future-checkpoint preapproval; routine operation authority carries through its persistence. Reuse acceptable existing main/feature inputs without interactive replay, prioritize requested interactive review and offer it for important startup concerns without assuming selection.
